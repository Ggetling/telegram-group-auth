# telegram-group-auth

[English](README.md) | **Русский**

Авторизация Telegram-бота по членству в группе. Добавьте бота в группу — и
каждый, кто в этой группе, становится пользователем бота. Администраторы
задаются отдельно и проходят всегда.

Никакого списка разрешённых пользователей вести не нужно. Никто никому ничего
не выдаёт. Человек вошёл в группу — бот у него работает; человека удалили —
перестал.

* **Ядро без зависимостей** и без всякого знания о фреймворках для ботов.
* **Адаптер для aiogram 3** в комплекте: две строки, чтобы поставить проверку,
  и один роутер на жизненный цикл группы.
* **Реестр пользователей необязателен** — по умолчанию в памяти, SQLite, если
  он должен переживать перезапуск.
* 93 теста, для запуска не нужны ни сеть, ни токен.

Написано для агентов не меньше, чем для людей: [AGENTS.md](AGENTS.md) — это
готовый рецепт того, как встроить это в уже существующего бота.

## Ограничение, о котором нужно знать раньше всего остального

**Бот не может получить список участников группы.** В Bot API нет такого
метода: `getChatAdministrators` возвращает только администраторов,
`getChatMemberCount` — число. Поэтому членство проверяется по одному человеку,
в тот момент, когда он пишет, и кешируется:

```
человек пишет  ->  он в admin_ids?             -> да: пропустить, всегда
                   ->  нет ->  есть в кеше?    -> да: взять оттуда
                                -> нет ->  getChatMember(группа, человек)
                                            -> участник:  пропустить, кеш 5 мин
                                            -> нет:       отказать, кеш 1 мин
                                            -> спросить не удалось: была удачная
                                               проверка за последние 15 мин?
                                               да — пропустить, иначе отказать
```

Для человека это ровно то поведение, которого от системы и хотят. Чего она не
даёт — так это списка ваших пользователей: реестр в этом пакете содержит лишь
тех, о ком Telegram успел сообщить сам, и он никогда не полон. Не стройте на
нём рассылку и не называйте её полной.

## Быстрый старт

Попробуйте пример бота — ему нужен сам репозиторий:

```bash
git clone https://github.com/OWNER/telegram-group-auth && cd telegram-group-auth
pip install -e ".[aiogram]"
export BOT_TOKEN=...          # у @BotFather
export AUTH_ADMIN_IDS=...     # ваш числовой id, у @userinfobot
python examples/minimal_bot.py
```

Добавьте бота в группу **администратором этой группы**. Теперь ему может писать
любой её участник.

Во всех этих документах `OWNER` — это аккаунт, на котором лежит репозиторий;
он есть в ссылке, которую вам дали.

В уже существующем боте на aiogram 3:

```python
from group_auth import AuthConfig, MembershipChecker, SqliteStore
from group_auth.aiogram3 import install, lifecycle_router

checker = MembershipChecker(AuthConfig.from_env(), store=SqliteStore("auth.db"))
await checker.load()

dp.include_router(lifecycle_router(checker))  # первым, до ваших роутеров
install(dp, checker)  # проверка, на всех точках входа
dp.include_router(your_router)

# Не опция: без этого Telegram вообще не пришлёт chat_member.
await dp.start_polling(bot, allowed_updates=dp.resolve_used_update_types())
```

Решение прокидывается прямо в хендлеры:

```python
@router.message(Command("start"))
async def start(message: Message, auth: Verdict, is_admin: bool) -> None: ...
```

## Настройка

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `AUTH_ADMIN_IDS` | пусто | Числовые id администраторов бота. Безусловный доступ, группа не нужна, и только они могут привязать группу |
| `AUTH_GROUP_IDS` | пусто | Группы, чьи участники являются пользователями. Достаточно членства в любой одной. Оставьте пустым, чтобы привязать группу добавлением бота в неё |
| `AUTH_CACHE_TTL` | `300` | Сколько секунд переиспользуется разрешение |
| `AUTH_DENY_CACHE_TTL` | `60` | Сколько секунд переиспользуется отказ. Намеренно мало: обычное лечение отказа — человека через пару секунд добавляют в группу |
| `AUTH_GRACE` | `900` | Сколько секунд доверять последней настоящей проверке, пока Telegram недоступен |
| `AUTH_PRIVATE_ONLY` | `1` | Игнорировать всё, что не личный чат. Бот сидит в группе, чтобы быть реестром, а не чтобы разговаривать |
| `AUTH_BIND_ON_ADD` | `admin_only` | `never`, `admin_only`, `first` или `always` — кому позволено привязать группу, добавив бота |

`AuthConfig.from_env(prefix="MYBOT_")` переименовывает их все сразу.

## Две вещи, которые ломаются молча

* **Обновления `chat_member` приходят только если бот — администратор
  группы.** Без этого входы и выходы видны лишь по служебным сообщениям
  («X присоединился») — это медленнее, но работает как запасной путь.
* **`chat_member` по умолчанию не входит в `allowed_updates`.** Запускайте
  polling с `allowed_updates=dp.resolve_used_update_types()`, иначе жизненный
  цикл группы будет невидим, и в логах не будет ни слова о причине.

## Про безопасность — стоит прочитать один раз

* `bind_on_add=admin_only` стоит по умолчанию потому, что кто может привязать
  группу, тот может выдать доступ кому захочет. Значение `always` отдаёт эту
  возможность любому, кто способен добавить вашего бота в чат.
* Администраторы обходят всё, включая сломанный Telegram API. В этом и смысл —
  кто-то должен иметь возможность починить бота, когда тот не работает, — но
  это значит, что `AUTH_ADMIN_IDS` не менее чувствителен, чем токен бота.
* Человек, удалённый из группы, сохраняет доступ до `AUTH_CACHE_TTL`, если бот
  не администратор группы; если администратор — обновление `chat_member`
  отзывает доступ сразу. Уменьшите `AUTH_CACHE_TTL`, если это окно для вас
  важнее, чем экономия вызовов API.
* Окно `AUTH_GRACE` — намеренный fail-open. `AUTH_GRACE=0` его выключает: тогда
  недоступный Telegram означает, что не проходит никто, кроме администраторов.

Обоснование каждого из этих решений — в [docs/DESIGN.md](docs/DESIGN.md), там
же список того, что действительно проверено, и того, что нет.
